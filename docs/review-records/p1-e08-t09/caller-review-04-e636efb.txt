## Findings

### R4-1 — P2: authenticate and validate the same predecessor-result bytes

**Location:** `packages/tools/src/capture/fauna_packet/caller.py:293-308`, combined with the new `verify_worktree` read at **351-353** and dispatch at 368-377.

`grant_gate` authenticates `result.json` with `sha(path)` and then separately reopens it with `read_json(result_path)` without passing the expected hash. The new `verify_worktree` correctly authenticates its own read, but uses that second object only for `raw.outputManifest`; it does not require that object's success/admission fields to be the ones validated by the gate.

The actual main/consume boundary admitted and executed unit 2 even though the exact result bytes referenced by its grant had `checksPassed:false` and a non-null `primaryFailure`:

1. A real first caller process runs the exact main/consume/run_unit/persist bodies with inert capture and decoder ports; the parent observes OS exit 0.
2. In scratch, the result is altered to a failed receipt before the next grant is hashed. The parent completion uses that actual exit 0 and exact hashes of the now-failed result and unchanged consumption. No exit status is fabricated.
3. A deterministic filesystem schedule replaces that receipt with the original successful bytes immediately after `sha()` hashes the failed bytes.
4. `grant_gate` parses the successful replacement and passes its checks. After that real JSON read, the schedule restores the failed bytes.
5. `verify_worktree` reads the failed bytes, verifies their exact grant hash, and accepts their unchanged artifact manifest. Unit 2 creates consumption/output/evidence, calls the inert allocation/capture/decoder ports, and main returns 0.

All hashes and JSON reads execute their real implementation; hooks only schedule actual scratch-file replacement between those operations. The authenticated result remains failed at the end. This is not merely a failure to detect a harmless formatting change: the successful acceptance fields were never authenticated against the grant. It requires concurrent receipt replacement/corruption; the stable-file controls correctly refuse failed receipts.

**Repro:** `metadata-boundaries.py`, case `authenticated-failed-result-accepted-by-split-read`. Test command exits 0 because it asserts the bad behavior; `metadata-boundaries-results.json` records `secondMainReturn:0`, `boundResultChecksPassed:false`, `consumptionCreated:true`, the exact swap schedule and inert dispatch calls. Fixture retained at `tmp/metadata-race-h86hqjr3`.

**Correction:** Load each predecessor receipt once through a capped read that verifies its expected reference hash over the exact parsed bytes. Validate success/transaction fields and the output manifest from that authenticated result. Apply the same rule to consumption metadata. Reusing the validated object in `verify_worktree`, or independently authenticating and validating every subsequent read, closes the split. The new `read_json(..., expected_sha256=...)` supports the needed primitive already.

**Contract:** explicit review requirement that allowed predecessors are exact hashed successful evidence and failures refuse before allocation/dispatch. The separate hash/parse pattern is inherited from the parent, not a newly introduced R3 regression; the R4 manifest reread leaves this gap open in the now-integrated admission path.

### R4-2 — P2: enforce receipt size limits before hashing predecessor files

**Location:** `packages/tools/src/capture/fauna_packet/caller.py:295-300`, calling the EOF-driven `sha` loop at **47-52** before the guarded JSON read at 56-63.

The new manifest reader is bounded, but admission gets to it only after `grant_gate` fully hashes both predecessor metadata files. An oversized/tampered receipt is therefore read to EOF before any JSON size guard runs. Streaming in 1 MiB blocks limits temporary memory; it does not limit total input bytes or processing time. This phase is also outside the capture/cleanup deadlines.

After an actual first caller OS exit 0, the independent test appends 8 MiB to each metadata type in separate fresh repositories, keeping the original grant hash. Actual second main/consume reads:

- `result.json`: **8,413,681 bytes** before refusing hash drift.
- consumption JSON: **8,389,847 bytes** before refusing hash drift.

Both exceed `read_json`'s **2,097,152-byte** maximum. The test measures real `Path.open(...).read(n)` returns; no fake oversized stream or large native work is involved. Refusal occurs before allocation in these cases, but only after unbounded input processing. A much larger or growing file extends that work without the stated metadata cap.

**Repro:** `metadata-boundaries.py`, `oversized-result` and `oversized-consumption`; per-read requested/returned sizes and retained fixtures are in `metadata-boundaries-results.json`. Command exit 0 asserts the observed violation.

**Correction:** Use the existing bounded, hash-checking JSON read before semantic checks instead of the separate unbounded `sha(path)` pass. Check size before reading, allow at most maximum+1 bytes to detect growth, hash those bytes, then parse them. Keep output artifact stat/type/cap checks before their reads. This is an inherited admission gap exposed by the explicitly requested R4 bounded-read audit, not a changed memory-allocation budget.
